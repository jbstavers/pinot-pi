# Security and privacy

Pinot is a Pi package. Pi packages run with the user's full system permissions; installing this package is equivalent to trusting its TypeScript extension. Read the source before installation and trust only projects where the package should operate.

## Current boundary

Pinot provides setup/status, bounded background delegation, six generic workflow prompts, the package-owned Janitor skill, the durable Herdr-backed implementer, and the exact test-suite runner. Ledger scanning and launcher integration are deferred to Unit 5. Loading the extension registers commands/tools and performs no file writes. `/pinot-status` reads only Pinot's state metadata and supported Pi location metadata. `/pinot-setup` initializes Pinot's persistent base state; the implementer may create only its named child session directory beneath the setup-created implementer root.

Setup writes only under `~/.pinot-pi`, or the absolute `PINOT_STATE_DIR` override. It preflights every target before writing, creates directories with exact owner-only mode `0700`, and creates template/config files with exact mode `0600`. Existing state is never overwritten. Symlinks, non-directories, unsafe permissions, ownership conflicts, and conflicting paths stop setup with an error before partial state creation. Implementer sessions live under `implementer/sessions/<name>/`; checkpoints live under `implementer/checkpoints/<name>.md` and are regular-file/freshness checked.

Pinot does not copy Pi authentication, settings, session contents, or credentials. Delegation resolves only the selected provider through Pi's documented `ctx.modelRegistry.getProviderAuth(provider)` boundary. It writes one mode-0600 temporary bridge, passes only its path to the package-owned child bootstrap, and removes the bridge/workspace on success, failure, timeout, and cancellation. The child consumes and unlinks the bridge before registering the built-in provider with resolved API key, headers, and base URL; provider-scoped environment values are applied only in the child process. No token or bridge path is placed in argv, results, logs, or persistent state, and the parent never falls back to a full user auth/settings file.

Workers receive only read-only `read`, `grep`, `find`, and `ls` tools. Their paths are checked against the canonical project root and symlink escapes are rejected. This is a process/configuration boundary, not an OS sandbox: Pi packages still run with full user permissions. External-source scouting is rejected unless `externalSourceExtension` explicitly names a compatible user-provided extension; Pinot bundles neither web access nor RTK. Status runs only the read-only `herdr integration status` probe, reports that integration independently from active `HERDR_ENV`, and checks configured models through Pi's registry without auth resolution.

`/pinot-implement` and `/pinot-janitor` require `HERDR_ENV=1`, an active socket and parent pane, Herdr 0.7.5 or newer, a current Pi integration, and a matching project topology before they allow a durable writer or closeout specialist. Implementation starts use the immutable `implementation` profile by default; Janitor starts use the start-only `janitor` profile, explicitly load the package-owned skill, and record that profile in the child Pi session. Resume and lifecycle actions reject missing, invalid, or conflicting profile metadata rather than guessing. `pinot_native_herdr_implementer` checks these conditions before it resolves provider auth or creates a pane. It then requires an exact built-in model; custom provider behavior is rejected. The parent writes a one-use mode-0600 auth bridge under the owner-only Pinot implementer state root and passes only its path through the new pane environment. Package-relative child support validates the root/provider/model, consumes and unlinks the bridge before registering the built-in provider override, and the parent removes it on all outcomes. Credentials are never placed in command results, checkpoints, logs, or persistent session metadata. Public lifecycle details omit assignment/checkpoint text and session, checkpoint, cwd, and bridge paths; completed writing/wait content carries only bounded, redacted checkpoint-v4 text while details report mechanical presence/size/freshness.

The lifecycle is host-safe rather than a sandbox. It verifies named Herdr host, durable Pi session identity, pane, status, cwd, and checkpoint before writing actions or host-only close. Close refuses a missing/irregular checkpoint, unavailable/failed/pending guard, working/non-settled host, or unverified pane disappearance, and preserves the same durable session. `pinot_run_test_suite` similarly rejects shell syntax, proves project-local log roots are Git-ignored before creation/writing, permits external Pinot-state roots, keeps complete output in owner-only mode-0600 logs, and returns only mechanical status plus a logical log location.

## Workflow and history boundary

The six prompt templates and `pinot-janitor` skill are explicit package resources. They do not alter personal UI settings, copy project instructions, or assume a named provider/model. Implementation and Janitor refuse without valid Herdr and never fall back to editing from the root or using an ephemeral worker. Janitor is the sole writer during closeout and receives authority over only the assigned project plus an exact configured history-root exception.

Implementation history is user-owned and append-only. This unit pulls forward the history-schema scaffold for semantic provenance, safe exact specification/plan snapshots, root/child references, review, verification, deviations, remaining work, Janitor maintenance, and Debrief lookup pointers. Unit 5’s scanner, launcher, and no-overwrite integration remain unimplemented. It excludes transcripts, checkpoint bodies, credentials, authentication state, sessions, caches, generated reports, and uncertain inputs. Aggregate ledger report paths and coverage periods are references only and do not claim per-implementation attribution; the scanner is not part of this Unit 4 package slice.

## Reporting a concern

Do not include credentials, tokens, private prompts, session contents, or personal paths in an issue. Describe the affected public path, reproduction, impact, and a safe synthetic example. For a suspected secret exposure, stop sharing the material and use a private channel appropriate to the repository owner.

## Rollback and uninstall

Pi package removal removes package code, not `~/.pinot-pi`. Pinot does not silently delete history, configuration, or ledger data. Archive or remove that state only as an explicit user action after reviewing its contents.
